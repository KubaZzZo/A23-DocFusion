# 第一阶段：补齐短板，验证硬指标

**目标：** 每个模块独立可用，准确率>80%有数据证明，没有明显的功能缺口。

**解决的问题：**
- 模块一自然语言指令解析不稳定（当前最大痛点）
- 模块二准确率无量化数据（赛题硬指标）

- 不知道哪类实体提取最差、差多少

## 1.1 模块二准确率验证（最关键）

### 做什么
构建人工标注的测试数据集，运行准确率验证，确保>80%，针对性调优。

### 怎么做

**Step 1 — 准备测试数据（3-4小时）**

创建 `tests/fixtures/accuracy/` 目录，准备三类文档各10份：

```
tests/fixtures/accuracy/
├── contracts/          # 合同类 10份
│   ├── contract_01.txt
│   ├── contract_01_annotations.json  # 人工标注
│   └── ...
├── invoices/           # 发票/凭证类 10份
│   └── ...
├── reports/            # 报告/简历类 10份
│   └── ...
└── golden_data.json    # 汇总标注文件
```

每份文档的标注格式：
```json
{
  "document": "contract_01.txt",
  "text": "采购合同\n甲方：北京科技有限公司\n乙方：上海信息技术有限公司\n合同金额：人民币伍拾万元整（500,000.00元）\n签订日期：2024年3月15日\n...",
  "entities": [
    {"type": "organization", "value": "北京科技有限公司"},
    {"type": "organization", "value": "上海信息技术有限公司"},
    {"type": "amount", "value": "500,000.00元"},
    {"type": "date", "value": "2024年3月15日"},
    {"type": "phone", "value": "13800138000"}
  ]
}
```

**数据来源（按优先级）：**
1. 网上找公开的合同模板、发票样本 — 复制文本内容
2. 自己用 Word 编造几份 — 确保实体明确、好标注
3. 用现有 `data/uploads/` 中已上传的文档 — 手动标注实体

**不需要图片或真实文件，只需要纯文本 + 标注JSON。** 实体提取的输入是 `doc.raw_text`，所以只要文本就够了。

**Step 2 — 运行验证（0.5小时）**

```bash
# 用 accuracy_validator.py 跑验证
cd backend/
python -c "
import asyncio
from core.accuracy_validator import EntityAccuracyValidator
from core.entity_extractor import EntityExtractor

async def main():
    extractor = EntityExtractor()
    async def extract_fn(text):
        result = await extractor.extract(text)
        return result.get('entities', [])
    
    report = await EntityAccuracyValidator.validate(
        'tests/fixtures/accuracy/golden_data.json',
        extract_fn
    )
    print(report.summary_text())

asyncio.run(main())
"
```

**Step 3 — 分析结果，定位弱项（1小时）**

预期输出示例：
```

  [PASS] amount               P=92.3%  R=85.7%  F1=88.9%  (24/28)
  [FAIL] phone                P=75.0%  R=60.0%  F1=66.7%  (12/20)
  ...
============================================================
```

**Step 4 — 针对性调优（2小时）**

对于 F1 低于 80% 的实体类型：
- **phone 类低** → 检查正则预提取的正则表达式是否正确
- **address 类低** → 检查 LLM prompt 中对 address 的定义是否清晰
- **id_number 类低** → 可能训练数据中这类实体太少，考虑加强正则

调优手段：
1. 修改 `entity_extractor.py` 中的正则预提取规则
2. 修改 LLM prompt 中对特定实体类型的描述和示例
3. 降低低置信度验证的阈值（当前0.75）

调完重跑验证，直到所有类型 F1≥80% 或整体 F1≥80%。

### 解决什么问题
- 赛题要求"准确率高于80%"，必须有数据证明
- 知道哪些实体类型是弱项，有的放矢地调优
- 答辩时能拿出一份准确率验证报告，有说服力

**Step 2 — 上下文感知匹配（1小时）**

在匹配时不仅看字段名，还看同行/同列的其他字段名来消歧义：

```python
# 例如: 行1有"签约日期"和"交付日期"两个字段
# 如果实体中有两个date类型的值"2024-03-15"和"2024-06-30"
# 根据字段名和实体上下文的语义相似度来分配
```

**Step 3 — LLM 回退增强（0.5小时）**

当规则匹配置信度低时（如字段名与所有实体类型的同义词都不匹配），让 LLM 直接做匹配决策：

```python
MATCH_PROMPT = """你是一个数据匹配助手。

有以下实体可用: {entities}

如果某个字段没有合适的实体，值设为null。"""
```

### 解决什么问题
- "公司名称"字段能匹配到 entity_type=organization 的实体
- 同名实体（两个"日期"）能根据上下文区分
- 减少模板填写的空填率

## 2.1 端到端演示场景开发

### 做什么
编写一个完整的演示脚本，覆盖"校园采购合同审查与汇总"场景。

### 怎么做

**演示脚本 `demo_scripts/campus_procurement.py`：**

```python
"""
校园采购合同审查与汇总 — 端到端演示

流程:
  1. 上传3份采购合同 + 1张发票图片
  2. 解析 + OCR + 实体提取
  3. 跨文档实体融合（数据融合亮点）
  4. 自动填写采购汇总表
  5. 自然语言格式化输出文档
"""
import asyncio
import sys
from pathlib import Path

sys.path.insert(0, str(Path(__file__).parent.parent / "backend"))

from core.workflow_engine import WorkflowRunner, WorkflowContext
from core.workflow_engine import ExtractStep, CrossDocFusionStep, FillStep, FormatStep, GenerateSummaryStep
from core.document_parser import DocumentParser
from db.database import DocumentDAO, EntityDAO, TemplateDAO, session_scope

async def demo():
    print("=" * 60)
    print("  DocFusion 校园采购合同审查与汇总 — 演示")
    print("=" * 60)
    
    # Step 1: 上传文档（模拟）
    print("\n[Step 1] 上传文档...")
    files = [
        "demo_contract_001.docx",  # 采购合同A
        "demo_contract_002.docx",  # 采购合同B  
        "demo_contract_003.docx",  # 采购合同C
        "demo_invoice_001.png",    # 发票图片
    ]
    doc_ids = []
    for f in files:
        doc = DocumentDAO.create(f, Path(f).suffix.lstrip("."), str(f))
        doc_ids.append(doc.id)
    print(f"  已上传 {len(files)} 份文档, IDs: {doc_ids}")
    
    # Step 2: 文档理解 + 实体提取
    print("\n[Step 2] 文档理解与实体提取...")
    for doc_id in doc_ids:
        path = DocumentDAO.get_by_id(doc_id).file_path
        result = DocumentParser.parse(path)
        DocumentDAO.update_text(doc_id, result["text"])
        print(f"  Doc#{doc_id}: 解析完成, 文本长度 {len(result['text'])} 字符")
    
    # Step 3: 实体提取 + 跨文档融合
    print("\n[Step 3] 实体提取与跨文档融合...")
    ctx = WorkflowContext()
    
    def get_texts(doc_id):
        return DocumentDAO.get_by_id(doc_id)
    
    extract_step = ExtractStep(doc_ids, get_texts)
    await extract_step.run(ctx)
    print(f"  提取实体: {ctx.get('entity_count')} 个")
    
    fusion_step = CrossDocFusionStep(doc_ids)
    await fusion_step.run(ctx)
    cross = ctx.get("cross_doc", [])
    print(f"  跨文档关联实体: {len(cross)} 组")
    for item in cross[:5]:
        print(f"    [{item.entity_type}] {item.entity_value} — 出现在 {item.doc_count} 份文档中")
    
    # Step 4: 填写汇总表
    print("\n[Step 4] 自动填写采购汇总表...")
    template = TemplateDAO.get_all()[0]  # 第一个模板
    fill_step = FillStep(template.file_path)
    await fill_step.run(ctx)
    print(f"  填写完成, 准确率: {ctx.get('fill_accuracy', 0):.1%}")
    print(f"  输出文件: {ctx.get('filled_path')}")
    
    # Step 5: 格式化
    print("\n[Step 5] 自然语言格式化...")
    format_step = FormatStep("标题加粗居中，字号16，金额列标红，添加页脚'金陵科技学院采购处'")
    await format_step.run(ctx)
    print("  格式化完成")
    
    # Step 6: 生成汇总报告
    print("\n[Step 6] 生成数据融合汇总报告...")
    report_step = GenerateSummaryStep("生成一份供应商风险评估与采购汇总报告")
    await report_step.run(ctx)
    print(f"  报告路径: {ctx.get('report_path')}")
    
    print("\n" + "=" * 60)
    print("  演示完成！所有输出文件:")
    print(f"  填写表格: {ctx.get('filled_path')}")
    print(f"  汇总报告: {ctx.get('report_path')}")
    print("=" * 60)

if __name__ == "__main__":
    asyncio.run(demo())
```

### 解决什么问题
- 有可运行的演示脚本，不依赖手动点击UI
- 演示流程可控、结果可预期
- 展示数据融合亮点（跨文档实体关联）

```python
@router.get("/documents/extract-batch/progress")
async def extract_batch_progress(doc_ids: str):
    """批量提取进度推送"""
    async def event_stream():
        ids = [int(x) for x in doc_ids.split(",")]
        for i, doc_id in enumerate(ids):
            yield f"data: {json.dumps({'current': i+1, 'total': len(ids), 'doc_id': doc_id})}\n\n"
            # 执行提取...
            await asyncio.sleep(0.1)
        yield f"data: {json.dumps({'status': 'complete'})}\n\n"
    
    return StreamingResponse(event_stream(), media_type="text/event-stream")
```

### 解决什么问题
- 批量处理时用户知道进度
- 赛题要求"API异步调用"的体现

## 3.3 答辩准备

### 做什么
准备答辩 PPT 要点和现场演示预案。

### 怎么做

**PPT 要点（建议10页以内）：**

1. **问题定义** — 非结构化文档→人工提取→手动整理，痛点
2. **解决方案** — DocFusion 系统概述
3. **模块一** — 自然语言文档操作，Codex CLI 执行引擎
4. **模块二** — 多格式解析 + 多策略实体提取 + 准确率数据
5. **模块三** — 语义匹配 + 自动填写
6. **数据融合亮点** — 跨文档实体关联（核心技术展示）
7. **技术架构** — 三层设计，Docker部署
8. **演示** — 现场演示校园采购合同场景
9. **创新点** — Codex CLI作为执行引擎、多策略提取、跨文档融合
10. **总结与展望**

**现场演示预案：**
- **主路径**：运行演示脚本 `demo_scripts/campus_procurement.py`
- **备用路径**：如果网络不好，用本地 Swagger UI 手动演示
- **兜底方案**：如果 Codex CLI 调用失败，展示 LLM JSON 模式
- **关键画面**：跨文档融合结果、自然语言指令执行、自动填充的表格

### 解决什么问题
- 答辩时有结构化材料
- 演示有多层预案，不会冷场
- 技术亮点明确，评委能记住
