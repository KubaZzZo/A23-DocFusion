# DocFusion 代码质量与功能完整性深度分析

> 本文档聚焦代码层面和功能层面的问题，对项目各核心模块进行逐一「诊断式」评估。
> 结论：项目骨架搭建完成，但 **核心算法存在多处逻辑缺陷，功能覆盖度约 60-70%，远未达到竞赛可交付质量**。

---

## 一、最严重的代码缺陷（会直接导致错误结果）

### 1.1 SemanticMatcher 只返回每种类型的一个实体

**文件**: `backend/core/semantic_matcher.py:104-115`

```python
def _best_entities_by_type(entities: list[dict]) -> dict[str, dict]:
    best = {}
    for entity in entities:
        ...
        if current is None or confidence > current_confidence:
            best[entity_type] = entity  # ← 每种类型只保留一个
    return best
```

**问题**: 合同文档中典型场景：甲方=北京科技公司、乙方=上海工程集团，两者都是 `organization` 类型。当前代码只保留置信度最高的那个，另一个直接丢失。这意味着模板中的「甲方」和「乙方」字段不可能同时被填充。

**修复方向**: 改为 `dict[str, list[dict]]`，按 type 分组后在匹配阶段结合字段上下文选择最佳候选。

---

### 1.2 实体提取 MAX_CHUNK_CANDIDATES=3 导致长文档数据丢失

**文件**: `backend/core/entity_extractor.py:79, 194-205`

当文档超过 3 个 chunk 时，只选取关键词得分最高的 3 个 chunk 送入 LLM 提取。典型的 30 页合同可能被分为 10+ 个 chunk，超过 70% 的内容直接被跳过。

**后果**: 尾部附件中的联系方式、银行账号等关键实体完全不会被提取到。

---

### 1.3 验证阶段只截取前 3000 字符

**文件**: `backend/core/entity_extractor.py:169`

```python
context_text = original_text[:3000]
```

如果低置信度实体出自文档中后部分（第 3001 字符之后），验证 prompt 中根本没有对应原文，LLM 无法验证，大概率会标记 `verified=false` 误删正确实体。

---

### 1.4 WorkflowRunner 无错误恢复能力

**文件**: `backend/core/workflow_engine.py:189-197`

```python
for step in self.steps:
    try:
        result = await step.run(ctx)
    except Exception as exc:
        ctx.log("step_failed", ...)
        raise  # ← 直接向上抛出，无 retry、无 rollback
```

在三模块串行流水线中，如果 FillStep 因为 LLM 超时失败，整条流水线废弃，前面 ExtractStep 已经消耗的 LLM 调用（可能花了 30s+）全部浪费。竞赛演示时一次网络抖动就会导致全流程失败。

---

## 二、功能缺失（竞赛评分会扣分的点）

### 2.1 模板填充只支持表格首行表头模式

**文件**: `backend/core/template_filler.py:35-53`

```python
# 第一行作为表头
for cell in next(ws.iter_rows(min_row=1, max_row=1, ...), []):
```

**不支持的常见模板格式**:
- `{{姓名}}` 占位符模式（docx 正文或表格中的 placeholder）
- 表格左列为字段名、右列为待填充空格的「纵向布局」
- 多行合并单元格表头
- xls（旧格式）、csv 模板

竞赛样本中纵向布局模板极为常见（如个人信息表：左列"姓名""性别""出生日期"，右列空白），当前代码完全无法处理。

---

### 2.2 DocCommander 只处理 .docx 文件

**文件**: `backend/core/doc_commander.py:168-169`

```python
if Path(doc_path).suffix.lower() != ".docx":
    return {"success": False, "message": "DocCommander currently supports only .docx files"}
```

竞赛题目要求「文档理解」，但 PDF、.doc（旧格式）、.txt 均不支持。这意味着模块一的能力覆盖面严重不足。

---

### 2.3 正则提取只覆盖中文格式

**文件**: `backend/core/entity_extractor.py:80-85`

```python
"date": r"\d{4}年\d{1,2}月\d{1,2}日|\d{4}[-/.]\d{1,2}[-/.]\d{1,2}",
```

不支持的日期格式：`2026年3月`（无日）、`三月十五日`（中文数字）、`March 15, 2026`（英文）。
金额正则不支持：`12,000.50元`（带小数点+逗号千分位的组合）、`壹佰贰拾万元整`（大写金额）。

---

### 2.4 跨文档融合（CrossDocFusionStep）仅做统计，无冲突消解

**文件**: `backend/core/workflow_engine.py:121-135`

当前 CrossDocFusionStep 只是调用 `EntityDAO.get_cross_document_entities()` 做简单统计（出现次数、文档数），并没有实现真正的「数据融合」：
- 同一实体在不同文档中表述不一致时（如 "北京智远科技" vs "智远科技有限公司"），无法识别为同一实体
- 冲突值（如同一人电话号码在两个文档中不同）无法消解
- 缺少实体链接（entity linking）和共指消解（coreference resolution）

这是「数据融合」竞赛主题的核心功能，当前实现仅为占位。

---

### 2.5 accuracy_validator 只有框架，无真实测试数据

**文件**: `backend/core/accuracy_validator.py`

竞赛要求 F1 > 80%，但：
- `generate_sample_data()` 生成的是硬编码示例，不是真实测试集
- 没有 golden label 数据文件
- 评测从未在 CI 或测试套件中被调用
- fuzzy matching 用 substring 判断（`expected in actual or actual in expected`），这种方式 "北京" 会匹配 "北京智远科技有限公司"，F1 虚高

## 三、代码质量问题

### 3.1 安全问题

| 位置 | 问题 | 风险 |
|------|------|------|
| `template_filler.py:98` | `output_path.chmod(0o666)` | 所有用户可读写输出文件 |
| `doc_commander.py:206,304,610,648` | 4 处 `chmod(0o666)` | 备份文件和恢复文件全部 world-writable |
| `doc_commander.py:222-239` | subprocess 执行 codex CLI 无沙箱 | 生成的代码可执行任意系统命令 |
| `.env` 中 API key 明文 | `OPENAI_API_KEY=sk-...` | 泄露后可被盗用 |

### 3.2 错误处理粗糙

```python
# doc_commander.py:178-179
except Exception as exc:
    pass  # ← Codex失败后静默吞掉异常，无任何日志
```

多处 bare `except Exception: pass` 导致调试困难，生产环境中问题会被完全掩盖。

### 3.3 GenerateSummaryStep 静默截断数据

**文件**: `backend/core/workflow_engine.py:149-153`

```python
"entities": entities[:100],
"cross_document": [... for e in cross_doc[:50]],
```

当实体超过 100 个时，报告只基于前 100 个生成，但用户不会收到任何提示。对于批量处理场景（10+ 文档），100 个实体很容易被超出。

### 3.4 并发安全问题

- `TemplateFiller.fill()` 中 `shutil.copyfile` + `chmod` 不是原子操作
- `DocCommander._backup()` 用时间戳命名，同一秒内两次调用会覆盖
- `EntityExtractor` 的缓存 (`get_cached`/`set_cached`) 如果是 dict 实现，多协程并发写入可能丢数据

### 3.5 类型标注与代码风格

- `workflow_engine.py` 中 `get_texts` 参数类型为裸 `Callable`，无签名提示
- 多处 `dict` 返回值无 TypedDict/dataclass 定义，下游使用全靠猜 key
- `semantic_matcher.py:77` 调用 `self.llm.extract_json` 传入已格式化的 prompt 同时又传 user_input，职责不清

## 四、架构设计问题

### 4.1 模块间耦合

```
WorkflowEngine → EntityExtractor（直接实例化）
             → TemplateFiller（直接实例化）
             → DocCommander（直接实例化）
```

没有依赖注入，无法替换为 mock 进行单元测试。WorkflowRunner 的测试必须连接真实 LLM。

### 4.2 缓存策略单一

- 只有实体提取有缓存，模板分析和语义匹配没有
- 缓存 key 包含 base_url + model，切换模型后缓存全部失效
- 无缓存淘汰策略，长期运行内存持续增长

### 4.3 LLM 调用无成本控制

- 每个 chunk 一次 extract 调用 + 低置信度实体一次 verify 调用 + 语义匹配一次调用
- 一个 10 chunk 文档最多可能触发 3(extract) + 1(verify) + 1(match) = 5 次 LLM 调用
- 无 token 预算限制、无请求频率限制、无超时后降级策略

## 六、优先修复建议（按投入产出比排序）

### P0 - 必须修（影响核心评分）

1. **修复 SemanticMatcher 多实体匹配**
   - 改为按 type 分组返回列表
   - 匹配时结合字段名上下文选择（如 "甲方" 优先选第一个 organization）
   - 预计工作量：2-3h

2. **增加模板纵向布局支持**
   - 检测表格左列为标签、右列为空的模式
   - 支持 `{{placeholder}}` 正文占位符
   - 预计工作量：4-6h

3. **提升长文档实体覆盖率**
   - 将 MAX_CHUNK_CANDIDATES 提升到 5-8，或改为动态策略
   - 验证时使用实体所在 chunk 而非固定前 3000 字
   - 预计工作量：2-3h

4. **实现基础跨文档实体消解**
   - 基于编辑距离/Jaccard相似度做实体去重
   - 同 type 同值（模糊匹配 >0.8）合并为同一实体
   - 预计工作量：4-6h

### P1 - 应该修（影响演示效果）

5. **WorkflowRunner 加 retry + 部分结果保存**
   - step 失败后 retry 1 次
   - 已完成的 step 结果持久化，避免全部重来

6. **扩展正则模式**
   - 补充大写金额、英文日期、无年份日期等模式
   - 补充身份证号 18 位校验

7. **移除所有 chmod(0o666)**
   - 改为 `0o644` 或使用 umask 继承

8. **给 Codex 执行路径加异常日志**
   - 把 `except Exception: pass` 改为 `log.warning(...)`

### P2 - 锦上添花

9. 支持 PDF 和 .doc 格式读取（使用 pdfplumber/antiword）
10. 增加真实 golden test data 和 CI 自动评测
11. LLM 调用加 token budget 和 fallback 策略
12. 引入依赖注入，使各模块可独立测试

---

## 七、总结

项目整体架构设计合理（三级执行策略、流水线编排、缓存层），代码结构清晰，命名规范。但在核心算法的正确性和边界处理上存在**多处致命逻辑错误**（尤其是 SemanticMatcher 的单实体问题和长文档截断问题），功能覆盖面不足（模板只支持一种布局、文件只支持 docx、融合只是统计）。

**一句话评价：这是一个「能跑通 happy path」但「无法应对真实文档多样性」的系统。**

如果要参加竞赛评审，P0 级别的 4 个修复是必须完成的最低要求。
