## 一、项目概述

### 1.1 赛题背景

金陵科技学院 A23 赛题"文档理解与多源数据融合系统"，要求构建一个能够：
- 理解非结构化文档内容
- 自动提取关键信息
- 跨文档关联融合数据
- 通过自然语言交互操作文档

的智能化桌面/Web系统。

### 1.2 项目规模

| 指标 | 数值 |
|------|------|
| 总代码行数 | ~15,000 行 |
| Python 源文件 | 68 个 |
| 测试文件 | 16 个（96 个测试用例） |
| Git 提交 | 10 次 |
| 外部依赖 | ~25 个 Python 包 |
| 独立模块 | 3 个（frontend / backend / server_toolkit） |

### 1.3 技术栈

```
前端: PySide6 (Qt for Python)
后端: FastAPI + Uvicorn
数据库: SQLAlchemy 2.0 + SQLite
LLM: Ollama (本地) + OpenAI 兼容 API (云端)
文档处理: python-docx, openpyxl, PyMuPDF, pypdf
OCR: Tesseract + Pillow
AI Agent: Codex CLI
部署: Docker
安全: Windows DPAPI, magic bytes 验证, Bearer token
```

## 二、模块逐一分析

### 2.1 模块一：文档智能操作交互模块

**核心文件：** `backend/core/doc_commander.py`（~720行）

**三层执行路径：**

```
用户自然语言输入
  │
  ├── 路径1: 规则匹配 (0.1s)
  │   支持: 加粗/斜体/下划线/字号/颜色/对齐/中文序数
  │   覆盖: ~15% 的常见指令
  │   准确率: 高（确定性匹配）
  │
  ├── 路径2: Codex CLI 执行 (10-30s) [★ 主路径]
  │   支持: 任意复杂的文档操作
  │   覆盖: ~70% 的指令
  │   准确率: 中高（取决于 prompt 质量）
  │
  └── 路径3: LLM JSON 解析 + 直接执行 (2-5s) [兜底]
      支持: 5种 action (format/edit/find_replace/extract/structure)
      覆盖: ~60% 的指令
      准确率: 低（JSON 格式错误、幻觉、index 越界）
```

**支持的操作类型：**

| 操作 | 规则路径 | Codex CLI | LLM JSON |
|------|:---:|:---:|:---:|
| 段落加粗/斜体/下划线 | ✅ | ✅ | ✅ |
| 字体/字号设置 | ✅ | ✅ | ✅ |
| 文字颜色 | ✅ | ✅ | ✅ |
| 对齐方式 | ✅ | ✅ | ✅ |
| 段落编辑（增删改） | ❌ | ✅ | ✅ |
| 查找替换 | ❌ | ✅ | ✅ |
| 表格行格式化 | ❌ | ✅ | ✅ |
| 文本/表格/标题提取 | ❌ | ✅ | ✅ |
| 页面设置（页边距等） | ❌ | ✅ | ❌ |
| 行距/段落间距 | ❌ | ✅ | ❌ |
| 页眉页脚 | ❌ | ✅ | ❌ |
| 多段落组合操作 | ❌ | ✅ | ❌ |
| 图片操作 | ❌ | ✅ | ❌ |

**评分：60/100**

**优点：**
- 三层回退设计，理论覆盖率高
- Codex CLI 路径可以处理任意复杂的操作
- 规则引擎对常见指令响应极快（毫秒级）
- 有备份恢复机制，可变操作前自动备份

**缺点：**
- LLM JSON 路径极不可靠（见 4.1 节详细分析）
- 只支持 .docx 格式
- 不支持撤销/重做
- 段落索引与用户感知的段落编号不一致
- 错误提示不够友好（只返回技术错误信息）

### 2.2 模块二：非结构化文档信息提取模块

**核心文件：**
- `backend/core/document_parser.py` — 文档解析（~150行）
- `backend/core/entity_extractor.py` — 实体提取（~300行）
- `backend/core/text_chunker.py` — 文本分块（~60行）
- `backend/db/database.py` — 数据存取（~250行）

**处理流程：**

```
文档上传 → 签名验证 → FileTransaction → 保存
  ↓
解析: DocumentParser.parse()
  ├── .txt/.md  → 直接读取
  ├── .docx     → python-docx 提取段落+表格
  ├── .xlsx     → openpyxl 提取Sheet+单元格
  ├── .pdf      → PyMuPDF 提取文本
  └── .png/.jpg → Tesseract OCR
  ↓
分块: TextChunker.chunk()
  └── 按段落切分, 3000字符/块, 200字符重叠
     超长段落(>3000字符)强制按句子二次拆分
  ↓
提取: EntityExtractor.extract()
  ├── 策略1: 正则预提取 (email/phone/amount/date)
  ├── 策略2: 关键词密度评分 → 选最相关块
  ├── 策略3: LLM 提取 8种实体类型
  └── 策略4: 低置信度(<0.75) → LLM二次验证
  ↓
存储: EntityDAO.create_batch()
  └── SQLite, entity_type + entity_value 联合索引
  
融合: get_cross_document_entities()
  └── GROUP BY entity_type, entity_value
      HAVING COUNT(DISTINCT document_id) >= 2
```

**支持的实体类型：** person, organization, date, amount, phone, email, address, id_number（8种）

**评分：75/100**

**优点：**
- 多策略组合（正则+LLM+验证），比单纯LLM提取准确
- 低置信度验证机制减少了误提取
- 分块策略处理了长文档超出 LLM context window 的问题
- 跨文档实体融合是数据融合主题的直接体现
- 有双层缓存（内存LRU + 磁盘文件）
- 适配器模式易于扩展新格式

**缺点：**
- 准确率未量化验证（赛题要求>80%）
- 无法由用户自定义实体类型
- 实体间关系未被提取（张三和北京科技是雇佣关系？合同关系？）
- PDF 表格提取能力弱
- OCR 中文准确率依赖 Tesseract 中文语言包质量
- 没有实体去重的语义判断（"北京科技有限公司" vs "北京科技" 是否同一实体？）

### 2.3 模块三：表格自定义数据填写模块

**核心文件：**
- `backend/core/template_filler.py` — 模板填写（~140行）
- `backend/core/semantic_matcher.py` — 语义匹配（~100行）

**处理流程：**

```
模板上传 → analyze_template()
  ├── .xlsx → 读第一行表头 → 扫描空单元格
  └── .docx → 读表格第一行表头 → 扫描空单元格
  ↓
填写: fill()
  ├── 分析模板字段名列表
  ├── SemanticMatcher.match(字段名, 实体列表)
  │   ├── 规则匹配: 字段名 ↔ 实体类型 关键词映射
  │   └── LLM回退: 未匹配字段让LLM选最合适的实体
  └── 执行填写
      ├── .xlsx → openpyxl 写入单元格
      └── .docx → python-docx 填入表格单元格
```

**评分：65/100**

**优点：**
- 支持 .xlsx 和 .docx 两种常见模板格式
- 自动检测空白单元格，无需用户手动标记
- 有公式注入防护（`escape_formula_value`）
- 保留原模板格式

**缺点：**
- 匹配准确率受限于同义词表覆盖度（"公司名称" ≠ "甲方"）
- 不支持合并单元格的复杂表格
- 只能填空白单元格，不能覆盖已有占位内容
- 多 Sheet 的 xlsx 只处理第一个 Sheet
- docx 模板只能用 `{{field}}` 占位符，不够灵活
- 匹配失败时没有提示用户手动干预的机制

### 2.4 跨文档数据融合（加分项）

**核心实现：** `EntityDAO.get_cross_document_entities()`

```sql
SELECT entity_type, entity_value,
       COUNT(DISTINCT document_id) AS doc_count,
       COUNT(*) AS total_occurrences
FROM entities
WHERE document_id IN (?, ?, ...)
GROUP BY entity_type, entity_value
HAVING COUNT(DISTINCT document_id) >= 2
ORDER BY doc_count DESC
```

**评分：70/100**

**优点：**
- 简洁高效的 SQL 聚合实现
- 直接体现"数据融合"主题
- 可以扩展到实体冲突检测、时间线构建

**缺点：**
- 只有精确匹配（entity_value 完全相同才算关联）
- 没有模糊匹配（"北京科技" 和 "北京科技有限公司"）
- 没有实体关系分析
- 没有可视化展示

## 四、缺点与问题清单

### 4.1 严重问题（必须在提交前修复）

#### P0-1：模块二准确率无量化证明

**问题：** 赛题明确要求"准确率需高于80%"，但当前没有任何测试数据证明。

**影响：** 评委可能直接判定不满足技术要求。

**修复：** 第一阶段完成准确率验证（详见三阶段计划）。

#### P0-2：模块一 LLM JSON 解析不可靠

**问题：** LLM 输出的 JSON 经常：
- 格式错误（缺少引号、多余逗号、markdown 代码块包裹）
- 幻觉操作（对不存在的段落 index 执行操作）
- 类型错误（color 字段返回字符串而非 RGB 数组）

**根因：** 让 LLM 同时做"意图理解"和"结构化输出"，错误概率叠加。

**现状：** 已通过引入 Codex CLI 作为主路径缓解，但 LLM JSON 路径仍在兜底使用。

#### P0-3：三个模块之间断开

**问题：** 模块二提取的实体 → 模块三不能自动使用，需要手动触发。模块三填写的结果 → 模块一不能自动格式化。用户无法用一句话驱动整个流程。

**现状：** 已通过 `workflow_engine.py` 部分解决，但缺少前端入口。

### 4.2 中等问题（影响体验和演示效果）

#### P1-1：只支持 .docx 格式的文件操作

模块一的 `execute()` 方法硬编码拒绝对非 docx 文件的操作。用户上传 PDF 后无法用自然语言操作。

#### P1-2：桌面 UI 过重

`docfusion_page.py` 约 2200 行，5 个 Tab 页。维护成本高，演示时容易出问题。

#### P1-3：SemanticMatcher 匹配覆盖率低

字段名"甲方"无法匹配 entity_type=organization 的实体，因为没有同义词映射。

#### P1-4：无错误恢复引导

当操作失败时，用户只看到技术错误信息（如 "Paragraph index 5 is out of range"），没有引导用户如何修正。

#### P1-5：Codex CLI 依赖VPS环境

本地开发时如果没有 Codex CLI，模块一只能走不可靠的 LLM JSON 路径。

#### P1-6：爬虫模块与主题无关

`backend/crawler/news_spider.py` 提供的新闻爬虫功能与"文档理解与数据融合"主题没有直接关系。

### 4.3 轻微问题（影响完整度但不致命）

#### P2-1：实体关系未提取

当前只提取独立实体，不提取实体间的关系。例如"张三 是 北京科技有限公司 的 联系人"这个三元组没有被提取。

#### P2-2：无文档级去重

同一文件上传两次会创建两条记录。

#### P2-3：API 客户端使用 urllib

`frontend/api_client.py` 使用标准库 urllib 而非 requests/httpx，需要手动处理 multipart、token、错误提取。

#### P2-4：测试覆盖不均

server_toolkit 有 79 个测试，backend 只有 3 个回归测试，frontend 只有 12 个边缘测试。

#### P2-5：配置散落

配置散落在 `config.py`、环境变量、`settings.json` 三处，没有统一的配置中心。

## 五、测试指标体系

### 5.1 模块二：实体提取准确率

这是赛题唯一明确量化的指标。**必须达到 >80%。**

#### 测试方法

```
测试集: 30份以上文档，覆盖3种以上类型
标注: 人工标注每份文档中的实体 (type, value)
执行: EntityExtractor.extract() 对每份文档提取实体
对比: 提取结果 vs 标注结果
计算: Precision / Recall / F1
```

#### 测试指标定义

| 指标 | 公式 | 含义 | 目标 |
|------|------|------|:---:|
| Precision (准确率) | TP / (TP + FP) | 提取的实体中有多少是正确的 | ≥ 80% |
| Recall (召回率) | TP / (TP + FN) | 正确的实体中有多少被提取出来 | ≥ 80% |
| F1 Score | 2 × P × R / (P + R) | 准确率和召回率的调和平均 | ≥ 80% |

其中：
- TP (True Positive)：提取的实体与标注匹配
- FP (False Positive)：提取了标注中没有的实体
- FN (False Negative)：标注的实体没有被提取

#### 分类型指标

每个实体类型单独计算：

```
person:        P=??  R=??  F1=??
organization:  P=??  R=??  F1=??
date:          P=??  R=??  F1=??
amount:        P=??  R=??  F1=??
phone:         P=??  R=??  F1=??
email:         P=??  R=??  F1=??
address:       P=??  R=??  F1=??
id_number:     P=??  R=??  F1=??
```

#### 验收标准

- [ ] 整体 F1 ≥ 80%
- [ ] 每个实体类型的 F1 不低于 60%（不能有某个类型完全无法识别）
- [ ] 正则预提取的类型（email, phone）F1 ≥ 90%
- [ ] 至少 3 种实体类型 F1 ≥ 85%

### 5.2 模块一：指令执行成功率

#### 测试方法

准备 N 条覆盖不同操作类型的自然语言指令，统计执行成功率。

#### 测试用例

```python
TEST_COMMANDS = [
    # 简单格式 (预期走规则路径)
    ("把第一段加粗", "format", True),
    ("第二段居中显示", "format", True),
    ("将标题字号改为18", "format", True),
    
    # 中等复杂 (预期走 Codex CLI)
    ("把所有金额数字标红并加粗", "format+find_replace", True),
    ("给文档添加页眉'内部文件'", "structure", True),
    ("第三段字体改为黑体14号并加下划线", "format_combo", True),
    
    # 复杂操作
    ("将表格中所有空单元格填充为'N/A'", "table+edit", True),
    ("删除第五段，把第四段和第六段合并", "edit_combo", True),
    ("设置页边距为上下2.5cm左右3cm", "page_setup", True),
    
    # 提取操作
    ("提取文档中所有表格", "extract", True),
    ("列出所有标题", "extract", True),
    
    # 边缘情况
    ("把倒数第二段删除", "fuzzy_index", False),  # 模糊索引
    ("把文档中很长的那个段落加粗", "fuzzy_desc", False),  # 模糊描述
]
```

#### 验收标准

- [ ] 简单指令成功率 ≥ 95%（规则路径）
- [ ] 中等复杂指令成功率 ≥ 85%（Codex CLI 路径）
- [ ] 复杂指令成功率 ≥ 70%
- [ ] 整体成功率 ≥ 80%

### 5.3 模块三：模板填写匹配率

#### 测试方法

准备 5-10 个模板文件和对应的实体数据集，统计字段匹配成功率。

#### 测试指标

| 指标 | 定义 | 目标 |
|------|------|:---:|

#### 验收标准

- [ ] 字段匹配率 ≥ 80%
- [ ] 同义词映射后匹配率提升 ≥ 15%
- [ ] 模板格式保持率 ≥ 90%（填写后格式无明显错乱）

### 5.5 安全指标
